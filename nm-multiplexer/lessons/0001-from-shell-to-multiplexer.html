Build your multiplexer · Lesson 0001

From a shell demo to a multiplexer

A codebase-based roadmap: each step should leave you with a running, testable slice.

Your current PTY code proves the core interaction: a local process can be attached to a pseudo-terminal, with terminal input and output copied between the user terminal and the PTY. A multiplexer changes who owns that PTY: the server owns it; a client temporarily carries bytes between the user and server.

your terminal ⇄ client ⇄ Unix socket ⇄ server ⇄ PTY ⇄ shell

What exists today

  • main.go starts a local Bash PTY and copies stdin/stdout. It is a useful prototype, but not yet a server-owned shell.
  • server/server.go listens on a Unix socket and exposes HTTP health/memory endpoints. It does not yet own a PTY or accept interactive clients.
  • client/client.go contains a second local-shell prototype; it currently duplicates the PTY work instead of connecting to the server.
  • go test ./... currently fails because root-level main.go and test.go both declare main. Also, both client and server declare package main, so they are executable packages, not importable libraries.
Design principle: keep the first milestone deliberately small. One server, one shell, one attached client. Sessions, panes, and a terminal screen emulator can wait.

Next steps, in learning order

1 · Make the project build cleanly

Remove or relocate the scratch test.go entry point, then establish clear server/client commands and run go test ./.... This gives every later change a reliable feedback loop.

2 · Make PTY ownership explicit

Extract a small server-side shell lifecycle: start one command under a PTY, expose its reader/writer, propagate terminal size, and wait for process exit. Decide who closes the PTY and how errors reach the caller. Test the lifecycle without requiring an interactive human.

3 · Define the smallest wire protocol

Use the Unix stream connection to carry client input to the PTY and PTY output to the client. Start with opaque bytes; a stream is not made message-based by socket reads. Add framing only when you need control messages such as resize, detach, or status.

4 · Attach one client end-to-end

The server accepts one client and bridges both directions. The client enters raw terminal mode, copies input/output, restores terminal state on every exit path, and reports disconnects cleanly.

5 · Make the shell survive detach

Separate shell lifetime from connection lifetime. A client disconnect should stop the bridge, not close the PTY or kill the shell. Reconnect and prove the same shell is still running.

6 · Add resize and lifecycle edges

Send terminal dimensions as a control message; handle resize, server shutdown, shell exit, stale socket cleanup, and simultaneous read/write failures. Only then consider multiple clients or sessions.

Your first small task

Before adding features, make go test ./... pass. Inspect why the extra root main breaks the build, choose where the runnable programs should live, and write down the package layout you intend to keep. Bring me your proposed layout or code and I’ll review it before the next lesson.
