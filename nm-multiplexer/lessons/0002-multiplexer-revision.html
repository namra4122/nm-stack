Build your multiplexer · Lesson 0002 · ~10 min

How a multiplexer works — revision

Recall first, then check. The win: you can draw the whole byte path from keyboard to shell and back, and say who owns each piece, before writing the server.

1 · Recall before reading

Take two minutes and do this without scrolling down: on paper, draw every hop a keystroke takes from your keyboard to bash running under a multiplexer, and the hops output takes back. Mark which process lives longest. Retrieving from memory, even imperfectly, is what makes it stick.

Reveal the answer once you've drawn it
keyboard→your terminal (raw mode)⇄client⇄Unix socket⇄server⇄PTY master⇄line discipline⇄PTY slave⇄bash

Shaded = outlives any client. The client is a short-lived pipe; everything from the server rightwards stays alive across detach.

2 · The six ideas, compressed

① A PTY is a pair of devices

“A pair of virtual character devices that provide a bidirectional communication channel. One end is called the master; the other … the slave.” The slave “behaves exactly like a classical terminal” — so bash believes it has a real terminal. pty(7). In your code, pty.Start(cmd) returns the master; the slave becomes bash's stdin/stdout/stderr.

② The line discipline sits in between

The kernel's TTY layer does echo, line editing in cooked mode, and turns ^C into SIGINT for the foreground job (Åkesson, “The TTY demystified”). That is why your client puts its own terminal into raw mode with term.MakeRaw: otherwise the outer terminal would edit and interpret keys first, and the inner shell's line discipline would never see them as typed.

③ The server owns the state

“tmux keeps all its state in a single main process, called the tmux server,” which “manages all the programs running inside tmux and keeps track of their output.” Users attach “by starting a client,” which “talks to the server using a socket file in /tmp.” (tmux wiki, Getting Started)

④ Detach = the connection ends, nothing else

Detaching means “the client exits … leaving the tmux session and any programs inside it running in the background” (tmux wiki). Contrast a plain terminal: on hangup, SIGHUP goes “to the entire session … Normally, this will kill all the processes”; programs like screen “detach from their session (and TTY), so that their child processes won't notice a hangup” (Åkesson). Your server is that escape hatch: the shell's controlling terminal is the server's PTY, not your real one.

⑤ Resize is a side channel

“The TTY device keeps track of the terminal size, but this information needs to be updated manually”; when it changes, it “sends SIGWINCH to the foreground job” (Åkesson). So the client must tell the server its new size; the server sets the PTY size (what pty.InheritSize / pty.Setsize do); the kernel signals bash. Size is not keystrokes — it needs a message that isn't just raw bytes. This is the first reason your protocol needs framing.

⑥ Reattach needs memory

Reason it through: if the server only forwards bytes as they arrive, a client attaching later receives only future output — a blank screen until something prints. A real multiplexer therefore keeps track of pane output (③) so it can redraw the current screen for a newly attached client. For your first slice, accepting “blank until next output” is fine; it's a later milestone.

3 · Check yourself

Answer from memory. Feedback is immediate.

4 · Map it onto your code

Open client/client.go. Every line in it today belongs to one of two future homes. Before the next lesson, annotate it (comments are fine): which lines move to the server (exec.Command, pty.Start, applying size) and which stay in the client (term.MakeRaw/Restore, watching SIGWINCH, copying stdin/stdout)? The one surprising line is pty.InheritSize(os.Stdin, nmux) — it reads the size on one side and applies it on the other, so it has to be split in two. Bring your split and we'll turn it into the server.

Primary source

Read Linus Åkesson — “The TTY demystified”, sections The use cases, SIGHUP and SIGWINCH. It's the clearest explanation of why the server-owned PTY works at all. Then skim the tmux Getting Started section on clients and servers.
